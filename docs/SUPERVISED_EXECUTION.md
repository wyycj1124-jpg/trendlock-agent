# MCP 监督执行

这一阶段的目标不是绕过 Binance MCP 的确认，而是把“盯盘发现该移动止损”自动化，把真正的账户写操作留给用户确认。

## 当前实现

```text
Binance 公开标记价格（每 5 秒）
              │
              ▼
      确定性阶梯状态机
      初始硬止损 −7%
      +5% → 锁 +2%
      +8% → 锁 +5%
      +11% → 锁 +8%
      +15% → ATR 宽幅追踪
              │
              ▼
        待确认改单队列
              │ 复制指令
              ▼
Codex + Binance MCP：读取 → 展示 → 用户确认 → 执行 → 读回
              │
              ▼
       用户记录核验结果
```

- 百分比始终相对真实加权开仓均价，不使用杠杆后的 ROE。
- `+15%` 后使用 `clamp(1.5 × 1h ATR(14), 5%, 8%)` 作为峰值回撤带，并设置 `+10%` 最低锁盈；保护价仍只能收紧。
- 当前默认单笔账户风险预算为 10%，初始硬止损为 7%；这是激进参数，风险预算不是实际亏损上限保证。
- 监控只订阅已有持仓的交易对，不持续扫描所有山寨币。
- 当前站点使用公开 REST 每 5 秒取标记价格，页面必须保持打开，电脑也不能休眠。
- 状态保存在当前浏览器。刷新或离开后任务恢复为 `HALTED`，必须重新读取账户对账。
- 现有止损必须先挂在 Binance 服务器。网页断线不会撤掉它，但断线期间也不会提高止损。

## 一次安全改单

1. 状态机只计算比当前服务器止损更紧的新价格；永不自动放松。
2. 页面创建 `WAITING_CONFIRMATION` 动作，但不修改“当前服务器止损”。
3. 复制 MCP 指令。MCP 先读取真实持仓、持仓模式、当前保护单和交易规则。
4. 用户查看完整参数后确认写操作。
5. 执行端创建更紧保护并读回验证。是否能先新建再撤旧单要以交易所实际规则和返回为准；不能假定原子替换。
6. Binance 同方向不允许两张 `closePosition=true` 保护同时存在；本 MCP 人工流程对阶梯改单返回 `EXECUTION_BLOCKED`，不通过两次独立确认制造长时间裸仓。
7. 只有读回结果与请求一致，用户才在页面记录新止损。

如果确认前价格已经回撤穿过请求的新止损，页面会废弃该动作并进入 `RECONCILIATION_REQUIRED`；不能拿已经失效的触发价继续下单。

## 何时扫描、何时监控

- 空仓选币：目标架构是在所选周期的已收盘 K 线出现时扫描一次，而不是每秒重扫市场。当前网页仍由用户手动点击扫描。
- 已成交持仓：当前网页每 5 秒读取一个交易对的标记价格，连续三次失败或间隔超过 30 秒即熔断。
- 持仓/订单变化：当前版本依靠 MCP 在每次动作前读回。24/7 版本应另外使用 Binance 用户数据流接收订单和持仓更新。

网页的 5 秒盯价与确定性状态机不调用模型，不产生 Codex token 消耗。模型巡检只负责账户对账、异常解释和生成待确认动作；1 小时机会扫描应在新收盘 K 线出现后运行一次，避免在同一根 K 线上重复消耗。

## 24/7 下一阶段

真正的后台版本应运行在用户控制的本地常驻进程或服务器，而不是浏览器标签页：

1. 标记价格 WebSocket，仅订阅持仓交易对；断线后退避重连，并在连接老化前轮换。
2. 用户数据流接收订单、成交和持仓事件，REST 仅用于启动和异常对账。
3. 本地持久化状态机和幂等动作 ID，重启后先对账、禁止盲目续跑。
4. 保护单永远优先于策略逻辑；任何不一致都冻结新动作。
5. 通知用户确认，不在超时后自动批准。
6. 单笔、单日和全账户熔断，以及测试网/极小仓位分阶段验证。

Binance MCP 的确认策略决定了它适合“后台监控 + 人工批准”，不等同于无需人在场的高频执行器。
