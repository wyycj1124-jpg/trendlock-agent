# 双槽位审批编排

这一阶段把 TrendLock 从“手动点一个候选”扩展为“自动管理候选队列，人只确认具体订单”。它不是无人值守交易机器人。

## 状态流

```text
读取真实持仓/委托
        │
        ├─ 两个币种已占用 ─→ 静默等待，只检查异常
        │
        └─ 有空槽位 ─→ 新扫描 ─→ 排除已占用币种
                                      │
                                      ├─ 无 ≥90 分 ─→ 不下单
                                      │
                                      └─ 前 N 名 ─→ 只读预检
                                                          │
                                                          ├─ 缺少服务器保护能力 ─→ EXECUTION_BLOCKED
                                                          └─ 能力完整 ─→ 展示具体确认卡
```

## 占用规则

- 一个交易对的非零持仓或未成交开仓委托都占用一个槽位。
- 同币多空或多个订单仍按一个币种计数，但会标记为需要对账的复杂暴露。
- 保护性减仓单不额外占槽，但必须覆盖真实持仓数量。
- 一个槽位释放后，只能使用新扫描的两分钟内证据，不能复用上一轮候选。

## 风险数学

用户指定的 10% 在此模式是组合总风险预算。两个槽位各获得最多 5% 权益预算：

```text
每槽位风险预算 = 当前 U 本位权益 × 5%
趋势名义仓位 ≈ 风险预算 ÷（初始止损幅度 + 成本预留）
估算保证金 = 名义仓位 ÷ 杠杆
```

只有一个合格候选时仍只分配 5%，不会为了“用完预算”而加倍。费用、滑点、跳空、强平和平台故障仍可能使实际损失超过预算。

## 当前可用性

`lib/orchestrator.ts` 已实现确定性排名、空槽位补位、风险分配和只读 MCP 预检指令。`npm run approval:scan -- <权益> <已占用币种逗号列表>` 可从公开 Binance Futures REST 生成队列。

当前 Binance MCP 工具结构不足以安全创建并读回服务器保护单，原生合约网格也未暴露。所以页面没有可误触的实盘开仓按钮，只提供只读预检。
